The reconciliation: you're walking through two different doors.

When you edit in an incognito window, you're using *Google's own Sheets frontend*. For a sheet set to "anyone with the link can edit," the link itself is the credential — a capability URL. The docs app mints an anonymous session for you behind the scenes (that's why you show up as "Anonymous Wombat" in the presence indicators — you *do* have a session, just not an account), and it talks to Google's private, undocumented sync endpoints using its own cookies and XSRF tokens. That machinery is first-party only.

The public API at sheets.googleapis.com is a separate door with a different bouncer. It has no concept of an anonymous principal: every write request must carry an OAuth token identifying *some* account, and only then does Google check whether that account has edit rights under the sharing settings. "Anyone with the link can edit" never enters the picture, because the request dies at authentication, before authorization is even considered — hence the 401 CREDENTIALS_MISSING we saw, not a 403. API keys don't bridge the gap either: they identify a billing project, not a person, so Google restricts them to reads of public data.

Could you, in principle, replicate what the incognito browser does — grab anonymous session cookies and speak the private protocol? Yes, technically, but it's undocumented, brittle, bot-protected, and changes without notice. Not a foundation to build on. So the practical statement stands: *third-party code* can't write without OAuth, and the Apps Script is the cheapest way to be a first party.
